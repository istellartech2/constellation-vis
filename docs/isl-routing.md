# ISL 経路探索機能 — 理論と実装

*(Markdown 上のプレーンテキスト数式、LaTeX 不使用)*

地球上の 2 地点間を、衛星間通信リンク (ISL: Inter-Satellite Link) を経由して結ぶ最適経路を計算し、3D シーン上に可視化する機能のリファレンス。問題の本質は **「時刻で変わる幾何制約つきグラフ探索」** である。

UI は左パネルの**通信タブ**に集約されている: 地点 A/B の選択と有効化 → 経路が 3D 表示され、結果カード(総遅延・中継数・総距離・切替統計)とシーン右下の HUD に数値が出る。コスト重み・参加衛星・リンク距離・シェル別リンク方式・表示色は同タブ内で調整でき、時間窓スイープの「ISL 経路タイムライン解析」も結果カードから開ける。

---

## 1. 理論

### 1.1 問題の定式化

ある時刻 t におけるネットワークをグラフ G(t) = (V, E(t)) とする。

- **ノード V**: 地上 2 地点 {A, B} と、ユーザーが ISL 参加対象に選んだ衛星集合 S。
- **エッジ E(t)**: 時刻 t に幾何制約を満たすリンク。2 種類ある。
  - **GSL (Ground-Satellite Link)**: 地上地点と衛星の間のリンク。A, B のみが端点になれる。
  - **ISL (Inter-Satellite Link)**: 衛星間のリンク。

求めるものは、A から B への経路 P = (A, s1, s2, ..., sk, B) のうち、エッジコスト総和

```
C(P) = Σ_{e ∈ P} c(e)
```

を最小化するもの。c(e) は多目的コストのスカラー化(§1.4)。中継段数 k は制約せず、探索が自然に決める(多段中継はこれで自然に扱われる)。

エッジ集合 E(t) が衛星の運動により時々刻々変わるため、「時刻で変わる幾何制約つきグラフ探索」となる。

### 1.2 幾何制約(エッジ存在条件)

#### 1.2.1 GSL の存在条件

```
GSL(g, s) が存在 ⟺ elevation(g, s) >= minElevationDeg(g) かつ distance(g, s) <= maxRangeKm
```

- elevation は `satellite.ecfToLookAngles(observer, satEcf)` で計算する。
- minElevationDeg は地点ごとの設定値(既存局はその局の値、臨時地点は既定 10°)。
- 距離上限 `maxRangeKm` は ISL と共通の設定を使う。仰角条件だけでは、低仰角時にスラントレンジが数千 km に達する(例: 高度 550 km・仰角 3° で約 2,373 km)「かすめる」ような実用上あり得ない長距離 GSL が最短経路に選ばれてしまうため、距離でも制限する。
- 既存 `GroundStation` が持つ `visibilityMode` / `maxOffNadirDeg` はセンサ観測用の制約であり、通信リンクの成立条件には**使わない**(UI に注記あり)。

#### 1.2.2 ISL の存在条件

衛星 i, j の ECI 位置を r_i, r_j [km] とし、次の 3 条件の AND とする。

**(a) 地球遮蔽なし (Line of Sight)**

線分 r_i–r_j が「地球 + 大気マージン」球に交差しないこと。線分と地球中心 O(ECI 原点)の最短距離 d_min で判定する。

```
d      = r_j - r_i
t*     = clamp( dot(-r_i, d) / dot(d, d), 0, 1 )
p_near = r_i + t* · d
d_min  = |p_near|

LoS 成立 ⟺ d_min > R_e + h_margin
```

- R_e = 6378.137 km(赤道半径。安全側の評価になる)
- h_margin: 大気減衰・屈折を避けるためのグレージング高度マージン。既定 80 km、ユーザー設定可。
- t* のクランプが重要: クランプなしの「直線と球」の判定では、地球の反対側に伸ばした直線が球と交差するだけで偽陰性になる。線分判定にすることで、近接した 2 衛星や GEO–GEO のような長距離リンクも正しく扱える。

**(b) 最大リンク距離**

```
|r_j - r_i| <= d_max
```

d_max は通信端末の能力を表すパラメータ。既定 5,000 km(LEO 光 ISL の典型値のオーダー)、ユーザー設定可。LEO–GEO のような異種軌道間リンクでは距離スケールが桁で違うため、シェル別の上書きができる(§2.2)。シェルをまたぐリンクは両シェルの maxRangeKm の大きい方を採用する。

**(c) パターン制約(シェル別に選択)**

実運用のコンステレーションでは、ISL 相手は自由選択ではなく端末配置で決まる(例: Starlink の +Grid)。シェルごとにリンク方式を選べる:

- `dynamic`(既定): (a)(b) を満たす全ペアが候補。自由トポロジ。
- `gridPattern`: 同一面内の前後 2 機(平均近点角順)+ 隣接面の同スロット 2 機、の最大 4 リンクに限定。その上で (a)(b) も適用する。

`gridPattern` は物理的に現実的なだけでなく、候補生成が O(N) になるため大規模構成での高速化手段でもある(§1.7.3)。gridPattern はシェル内リンクにのみ適用され、シェルをまたぐリンクは常に dynamic 判定となる(面/スロット構造がシェル間では定義できないため)。

指向制約(スルーレート、視野角、太陽方向回避など)はスコープ外(§5)。

### 1.3 時変グラフの扱い — スナップショット近似

信号の伝播遅延は LEO 多段経由でも数十 ms のオーダー。一方、トポロジ(エッジ集合)が変化するタイムスケールは数秒〜数分。つまり

```
伝播時間 (~10^-2 s) << トポロジ変化時間 (~10^1–10^2 s)
```

であり、パケットが経路を通過する間にグラフは実質不変。よって **各時刻 t で静的グラフ G(t) を作り最短経路を解く「スナップショットモデル」** が第一近似として正当化される。store-and-forward(衛星でデータを保持して可視待ちする運用)を扱わない限り、時間展開は不要。

蓄積転送や「時間窓をまたぐ配送」を扱う場合は、各エッジの可視時間窓リスト(contact plan)を作り、Contact Graph Routing (CGR) や時間拡張グラフに移行することになる(将来拡張。§1.5.2 の残存可視時間の予測は contact plan 計算の部分集合になっている)。

### 1.4 エッジコストと multi-objective

#### 1.4.1 「等価遅延 [ms]」への統一

多目的の重み付き和は、各目的の単位・スケールが揃っていないと重みの意味がユーザーに伝わらない。そこで **全コスト成分を「等価遅延 ms」に換算して合算する**。ユーザー設定値も物理的に解釈可能な量になる。

```
c(e) = ( c_prop(e) + c_hop(e) + c_kind(e) + c_stab(e) ) × H(e)   [ms]

H(e) = 1 - β   (e が前回採用経路に含まれる場合。ヒステリシス、§1.5.1)
     = 1       (それ以外)
```

#### 1.4.2 コスト成分

| 成分 | 種類 | 定義 | ユーザー設定 | 既定値 |
|---|---|---|---|---|
| 伝播遅延 c_prop | 加算 | distance_km / 299792.458 × 1000 | なし(物理量) | — |
| 中継ペナルティ c_hop | 加算 | 一定値/エッジ(中継処理・キューイング相当) | hopPenaltyMs | 2 ms |
| リンク種別ペナルティ c_kind | 加算 | エッジ種別(GSL / ISL)ごとの加算値 | kindPenaltyMs | 0 ms |
| 安定性ペナルティ c_stab | 加算 | 残存可視時間ベース(§1.5.2) | stabilityWeightMs | 0(無効) |
| ヒステリシス H(e) | 乗算 | 前回経路エッジへの割引(§1.5.1) | switchDiscount β | 0.2 |

- c_hop はエッジごとに課金する。どの A–B 経路もエッジ数 = 経由衛星数 + 1 なので、「経由衛星ごとに課金」とは定数差しかなく最適経路は変わらない。表示上のホップ数は経由衛星数と定義する(§6)。
- 中継ペナルティを大きくすれば「中継数最小」寄り、0 にすれば「純遅延最小」寄りになり、スライダ 1 本で hop / latency のトレードオフを表現できる。
- c_kind により「ISL を避けたい(地上局中心)」「GSL を避けたい(宇宙区間中心)」等のポリシーを表現する。

#### 1.4.3 multi-objective の扱い

重み付き和のスカラー化を採用している。全成分非負なので Dijkstra がそのまま使え、ユーザーは UI で重みを変更して経路が変わる様子をインタラクティブに観察できる。厳密なパレート最適化(多目的ラベリング法、ε 制約法、k-shortest paths + 事後評価)は、パレートフロントの列挙が最悪指数個の解を持ち計算も UI も重くなるため採用していない(将来拡張。§5)。

### 1.5 経路安定性(頻繁な切り替えの抑制)

「その瞬間の最適」だけを毎回選ぶと、コストが拮抗した経路間でフラッピング(高頻度な張り替え)が起きる。2 つの独立した機構で抑制する。

#### 1.5.1 ヒステリシス

直前の採用経路 P_prev に含まれるエッジのコストを割引く。

```
c'(e) = c(e) × (1 - β)   if e ∈ P_prev
      = c(e)             otherwise
β = switchDiscount ∈ [0, 0.5]、既定 0.2
```

- 新経路が「β 割引を覆すほど」良い場合のみ切り替わる。β が実質的な切替閾値になる。
- 割引後もコストは非負なので Dijkstra の前提を壊さない。
- これは切替回数の厳密な最小化ではなく貪欲な抑制である(厳密化はオフライン問題になる。§5)。
- 効果の実測: Iridium 風シェル(66 機)の東京–NY スイープで、β = 0 → 0.2 により切替回数 4 → 1、総遅延の劣化 +4.6%(`tests/isl-hysteresis-scenario.test.ts`)。

#### 1.5.2 残存可視時間ペナルティ(先読み回避)

軌道要素は既知なので、各エッジ e について「今後も存在条件を満たし続ける残り時間 τ_e」を予測できる。

```
τ_e = min{ Δt > 0 : 時刻 t + Δt で条件 (a) or (b) が破れる }
```

計算法: t から前方ホライズン T_h(300 s)を粗い刻み(10 s)でサンプリングし、最初に条件が破れた区間を二分法で精密化する。破れなければ τ_e = T_h(打ち切り)。

ペナルティは「もうすぐ切れるリンクを避ける」形の単調減少関数で与える:

```
c_stab(e) = w_τ × max(0, 1 - τ_e / τ_min)   [ms]
τ_min: 安定とみなす残存時間の閾値(60 s)
w_τ  : ペナルティ上限(UI の「先読み回避」。既定 0 = 無効)
```

全エッジ × 前方サンプリングの伝播が走るため計算コストが高く、既定では無効。有効化時も Worker 内で実行される。

### 1.6 探索アルゴリズム

#### 1.6.1 二分ヒープ Dijkstra

- 全コスト成分が非負なので Dijkstra が適用可能。計算量 O((|E| + |V|) log |V|)。
- dist / prevNode / visited は密なノード id(0..N+1)に対する型付き配列(`Float64Array` / `Int32Array` / `Uint8Array`)で保持し、ヒステリシスの前回経路照合は数値エッジキー(§2.1 `edgeKey.ts`)の Set で行う。
- 始点 A・終点 B の単一ペア探索なので、B に到達した時点で打ち切る。
- **A* は不採用**: ベンチ実測で探索は支配項でなく(支配項は候補リンク生成)、座標をグラフ層に持ち込む複雑さとヒステリシス併用時の admissibility 補正(h に (1−β) を乗じる必要)に見合わないため。

#### 1.6.2 再計算周期

- 毎フレーム再計算は不要。トポロジ変化のタイムスケールに合わせ、**シミュレーション時間で recomputeIntervalSimS(既定 10 s)ごと**に再計算する。
- 倍速再生(最大 600×)ではシミュレーション 10 s = 実時間 約 17 ms になるため、**実時間の下限インターバル(200 ms)** を併設して二重にスロットルする。高倍速時は実時間側が支配する。
- 一時停止中はシミュレーション時刻が進まないため定期再計算は止まる。ただし**設定変更(地点・参加衛星・コスト)は一時停止中でも即時に 1 回再計算**する(計算中に届いた変更は計算完了後に必ず再送される)。
- 再計算の谷間のフレームでは、経路の**ノード列は固定のまま、線分端点の座標だけ**を毎フレーム更新する(衛星は動き続けるため)。

### 1.7 候補リンク生成

ナイーブな全ペア判定は O(N^2) で、N = 10,000 では 5×10^7 ペアとなり実時間で破綻する。3 つの生成器を使い分ける。

#### 1.7.1 ナイーブ全ペア(`naiveIslCandidates`)

全ペアを距離二乗判定(sqrt 不要)→ LoS 判定の順で早期棄却しながら列挙する。**一様グリッドとの完全一致テストの「正解生成器」**としても使われる(`tests/isl-candidates.test.ts`)。

```
d2 = |r_j - r_i|^2
if d2 > d_max^2: 棄却            # 乗算3回+比較のみ
else: LoS 判定 (§1.2.2 (a))
```

#### 1.7.2 一様グリッド(`uniformGridIslCandidates`)

- ECI 空間をセル一辺 L = d_max のボクセルに切り、各衛星をセルにハッシュ登録(O(N))。セルキーは数値パック(文字列ハッシュ回避)。
- 各衛星は自セル + 隣接 26 セルの衛星とだけペア判定する。|r_j − r_i| ≤ d_max のペアは必ず隣接セル内にあるため、**取りこぼしなし**(ナイーブ実装との一致テストで担保)。
- k-d tree / octree ではなく一様グリッドなのは、毎スナップショットで全点が動く用途では再構築 O(N) が最も単純で速いため。
- グリッドはシェルごとの d_max の最大値で切る(異種軌道間対応)。シェル別設定使用時は、同シェルペアを距離/LoS 判定前に除外する pair-filter を併用する。
- 注意: LEO 単一シェルではシェルの空間的広がり(直径 ~13,900 km)が既定 d_max(5,000 km)と同程度のため、セル数が高々 30 程度に留まり、漸近的な優位性が出るのは d_max が小さい場合や N が非常に大きい場合に限られる。

#### 1.7.3 gridPattern(`gridPatternIslCandidates`)

候補が「面内前後 2 + 隣接面同スロット 2」と構造で決まるため、候補生成が**探索なしの O(N)**。シェル定義(planes / count)から各衛星の (面番号, スロット番号) を割り当て、隣接関係は添字計算(巻き戻り含む)だけで求まる。大規模 Walker コンステレーションではこれが最速かつ最も現実に近い。

### 1.8 座標系・時刻

- **計算は ECI [km] で統一。** satellite.js の `propagate` 出力をそのまま使う。
- 地上地点は geodetic → `geodeticToEcf` → `ecfToEci(ecf, gmst)` で ECI 化(gmst = `satellite.gstime(simDate)`)。GSL の仰角判定のみ ECF 系の `ecfToLookAngles` を使い、同一 simDate の gmst を共有して整合させる。
- 1 スナップショットの全ノード位置は**同一の simDate で評価**する。
- 描画時のみシーン座標変換を適用する。軸の入替(X_scene = X_eci, Y_scene = Z_eci, Z_scene = −Y_eci)に加え、**正規化が非等方**(X, Z は赤道半径、Y は極半径で除算)である点に注意。経路頂点にも衛星点と同一の変換を使う。**グラフ計算モジュールにシーン座標は持ち込まない。**

### 2.2 データモデル

中心となる設定は `IslSettings`(`src/lib/isl/types.ts`):

```ts
interface IslSettings {
  enabled: boolean;
  endpointA: IslEndpoint | null;   // station(局参照) | adhoc(緯度経度直接入力)
  endpointB: IslEndpoint | null;
  excludedShellKeys: string[];     // 除外シェルの安定キー
  includeBaseSatellites: boolean;  // satellites.toml 由来の個別衛星を含めるか
  linkModel: IslLinkModel;         // mode / maxRangeKm(既定 5000) / losMarginKm(既定 80)
  shellLinkModels?: Record<string, Partial<IslLinkModel>>; // シェル別上書き
  cost: IslCostSettings;           // hopPenaltyMs / switchDiscount / kindPenaltyMs / stabilityWeightMs
  recomputeIntervalSimS: number;   // 既定 10
  gslColor: string;                // 経路の表示色(endpoint マーカーも同色を使用)
  islColor: string;
}
```

探索結果は `IslPathResult`(到達可否、経由衛星 index 列、エッジ列、総遅延/距離、hopCount、切替フラグ、診断値)。グラフのノード id 規約は「0..N−1 = 衛星 index、N = 地点 A、N+1 = 地点 B」。

`IslSettings` は viewState(localStorage)に永続化される(旧形式はバージョン付きマイグレーションで救済)。

### 2.3 参加衛星の解決と shellRanges

- 参加指定は「**除外シェルの安定キー集合 + 個別衛星フラグ**」という小さく安定した状態だけを保存し、実際の衛星 index への解決は **compute 直前(Worker/graph 層、`participants.ts`)に毎回**行う。解決できないキーは単に無視される(そのシェルは参加扱い)ため、シェル構成を変えても設定が壊れない。
- 事前解決した satnum リストを保存する方式は採らない。TOML 再パースのたびに satnum が振り直されるため陳腐化し、「新しい衛星配列に古いスナップショットを適用する」「全解除が全参加に反転する(空配列 = フィルタなしと衝突)」という不整合の温床になる。
- シェルの index 範囲(`IslShellRange[]`)は永続化せず、衛星配列を確定する唯一の場所(シナリオタブの「更新」、`tomlParsers.ts` の `generateShellRanges`)で**実際に生成された配列から**導出し、衛星配列と一体の App state として保持する。これにより「衛星配列と shellRanges が別のタイミングで更新されてずれる」余地を構造的に排除している。
- シナリオ更新時は地点 A/B の局参照も整合させる(`reconcileIslEndpoints`): 同名局が残っていれば座標を最新化、消えた局を参照する地点は未設定に初期化する。

### 2.4 UI 構成(通信タブ)

タブ列は **シナリオ / 通信 / 解析 / 表示**。ISL 経路探索と通信系の表示設定(経路色、地上局の通信範囲コーン)は通信タブに集約されている。

1. **地上局の通信範囲** — コーン表示のトグル・最小仰角・距離上限・色。
2. **衛星間経路探索(ISL)** — 地点 A/B(既存局 or 臨時地点)、A/B 入替、有効化トグル。以下は有効時のみ表示され、薄い背景色のグループとしてまとまる:
   - **結果** — 到達可否 / 総遅延・中継衛星数・総距離の KPI カード / 伝搬遅延と追加コストの内訳 / 切替統計。地点未設定時はガイドを表示。「タイムライン解析を開く」で解析モーダルを直接起動。
   - **経路の重み付け** — 中継ペナルティ / 切替えにくさ(ヒステリシス β)/ 先読み回避(w_τ)/ 種別ペナルティ(GSL/ISL)。説明は各行の ⓘ に格納。
   - **詳細設定** — 参加衛星(シェル・個別衛星)、リンク距離制限(maxRangeKm / losMarginKm)、シェル別リンク方式、経路の表示色。
   - **診断** — 候補エッジ数、計算時間、再計算間隔、Worker エラー表示。
3. **結果 HUD**(`IslHud.tsx`)— 有効時はシーン右下(時刻表示の上)に地点名・総遅延・ホップ数・切替回数を常駐表示。パネルを閉じていても見え、クリックで通信タブが開く。
4. **タイムライン解析**(`IslRoutingAnalysis.tsx`)— 時間窓(期間・刻み)を指定して Worker でスイープし、総遅延・ホップ数の時系列、切替イベント、到達可能率を ECharts で表示。

到達不能時は結果カードに「経路なし」を明示し、シーン上の経路線を消す。無効化時は計算・描画とも完全に停止する(Worker は初回有効化まで生成すらしない)。

### 2.5 Worker 構成

重い処理(伝播・候補生成・探索)は `islRoutingWorker` にオフロードされ、メインスレッドは 60 fps の描画に専念する。

- **configure**: 設定(参加・リンクモデル・コスト・shellRanges)は identity が変わったときだけ送る。
- **compute**: `{id, simDateIso, previousPathEdgeKeys}` の小さなメッセージ。Worker が satrec から独立に伝播してグラフ構築 + Dijkstra を実行する。requestId で古い応答を破棄し、in-flight 中は次の compute を送らない(設定変更は完了後に必ず再送)。
- **sweep**: タイムライン解析用。時間窓内をヒステリシスを引き継ぎながら逐次計算し、結果配列を一括返却する。
- シェル range が衛星配列の範囲外になるような不整合は Worker 側で検出し、理由付きの error 応答として診断欄に表示される。

### 2.6 描画

- 経路は**単一の `THREE.LineSegments`** + 事前確保 BufferAttribute(64 区間、超過時は倍々で再確保)+ `setDrawRange`。頂点を区間ごとに複製することで GSL/ISL の色分けを頂点カラーで濁りなく行う(LineStrip だと区間境界で色が線形補間されてしまう)。
- 毎フレーム、ノード列は固定のまま線分端点の座標だけをスクラッチベクトル再利用で更新する(アロケーションフリー)。色バッファは結果か色設定が変わったときだけ書き換える。
- 地点 A/B マーカーは経路色(gslColor / islColor)を再利用し、地球の自転に追従する。
- ジオメトリ・マテリアル・Worker は `SatelliteScene.dispose()` で確実に解放される。
- IslSettings の変更は `updateParams()` の非構造 live 更新経路に載り、シーン再構築を発生させない。

### 2.7 性能

`scripts/bench-isl.ts`(bun 実行)による実測(参考値):

| N | naive(d_max=5,000km) | uniformGrid(同) | gridPattern(同) | graph+Dijkstra 合計(d_max=1,500km) |
|---|---|---|---|---|
| 100 | 0.7 ms | 2.0 ms | 0.4 ms | ~1 ms |
| 1,000 | 5.9 ms | 7.5 ms | 0.7 ms | ~9 ms |
| 10,000 | ~700 ms | ~250 ms | 2.8 ms | ~74 ms |

- N = 10,000 の dynamic モード(現実的密度 d_max=1,500 km)で 1 回の再計算 ~74 ms(Worker 内)。gridPattern なら候補生成が 3 ms 未満で、さらに大規模でも余裕がある。
- 再計算はスロットル(sim 10 s / 実時間 ≥ 200 ms)されるため、メインスレッドのフレームレートには影響しない。

## 5. 既知の制限・将来拡張

| 項目 | 内容 |
|---|---|
| リンク容量・帯域 | 扱わない(単一フローの経路のみ)。将来はエッジ容量 + フロー問題 |
| 指向・機体制約 | ジンバル可動範囲、スルーレート、太陽・月方向の回避は未対応(§1.2.2 (c) の拡張点) |
| 電波/光リンクの物理モデル | リンクバジェットは距離上限 d_max で抽象化。将来 c_kind を距離依存関数に拡張可能 |
| 切替回数の厳密最小化 | ヒステリシスによる貪欲抑制のみ。時間区間全体の最適化は contact plan / CGR の導入後に検討 |
| パレート最適化 | 重み付き和のみ。「遅延 vs ホップ数のパレート図」は将来の解析パネル候補 |
| 多地点・多フロー | A/B の単一ペアのみ |
| SGP4 の GEO 精度 | deep space(SDP4)の精度特性は LEO と異なるが、可視化用途では許容 |
| A* 探索 | 不採用(§1.6.1 の理由)。候補生成が支配項である限り導入価値は低い |

## 6. 用語

- **ISL**: Inter-Satellite Link。衛星間通信リンク。
- **GSL**: Ground-Satellite Link。地上局(地点)と衛星のリンク。
- **+Grid**: 面内前後 2 機 + 隣接面 2 機と結ぶ代表的な ISL トポロジ(本実装の `gridPattern`)。
- **スナップショットモデル**: 時変グラフを各時刻の静的グラフの列として扱う近似。
- **ヒステリシス**: 現状維持側に閾値を設けて頻繁な状態遷移を防ぐ機構。
- **ホップ数 (hopCount)**: 経路が経由する衛星の数(= エッジ数 − 1)。A → 衛星 → B は 1 ホップ。
- **Contact Graph Routing (CGR)**: 可視時間窓(contact plan)を前提とした DTN 系経路制御。本実装では未対応(将来拡張)。
