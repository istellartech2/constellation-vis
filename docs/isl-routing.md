## 0. 目的と要求整理

地球上の 2 地点間を、衛星間通信リンク (ISL: Inter-Satellite Link) を経由して結ぶ最適経路を計算し、3D シーン上に可視化する。問題の本質は **「時刻で変わる幾何制約つきグラフ探索」** である。

## 1. 理論

### 1.1 問題の定式化

ある時刻 t におけるネットワークをグラフ G(t) = (V, E(t)) とする。

- **ノード V**: 地上 2 地点 {A, B} と、ユーザーが ISL 参加対象に選んだ衛星集合 S。
- **エッジ E(t)**: 時刻 t に幾何制約を満たすリンク。2 種類ある。
  - **GSL (Ground-Satellite Link)**: 地上地点と衛星の間のリンク。A, B のみが端点になれる。
  - **ISL (Inter-Satellite Link)**: 衛星間のリンク。

求めるものは、A から B への経路 P = (A, s1, s2, ..., sk, B) のうち、エッジコスト総和

```
C(P) = Σ_{e ∈ P} c(e)
```

を最小化するもの。c(e) は多目的コストのスカラー化(§1.4)。中継段数 k は制約せず、探索が自然に決める(多段中継の要求はこれで満たされる)。

エッジ集合 E(t) が衛星の運動により時々刻々変わるため、「時刻で変わる幾何制約つきグラフ探索」となる。

### 1.2 幾何制約(エッジ存在条件)

#### 1.2.1 GSL の存在条件

既存の可視判定 (`src/lib/visibility.ts`) をそのまま使う。

```
GSL(g, s) が存在 ⟺ elevation(g, s) >= minElevationDeg(g) かつ distance(g, s) <= maxRangeKm
```

- elevation は `satellite.ecfToLookAngles(observer, satEcf)` で計算(既存実装)。
- minElevationDeg は地点ごとの設定値(既存 `GroundStation.minElevationDeg`)。
- 判定は**仰角 + 最大リンク距離(`IslLinkModel.maxRangeKm`、ISL と共通)**とする。既存 `GroundStation` が持つ `visibilityMode` / `maxOffNadirDeg`(オフナディア制約)はセンサ観測用であり、通信リンクの成立条件には適用しない。既存局を地点 A/B に選んだ場合も無視する(ISL タブにその旨を注記表示する)。
- 実装メモ: `visibility.ts` のペア単位判定関数(`isVisibleFromPreparedObserver` 相当)は現状非公開のため、Phase 1 で export するか、`ecfToLookAngles` による同等の仰角判定を `isl/geometry.ts` に置く小リファクタを行う。
- **設計変更(Phase 2 運用フィードバック)**: 当初案は「仰角のみ」だったが、低仰角では LEO 衛星までのスラントレンジが数千 km に達し(例: 高度 550 km・仰角 3°で約 2,373 km)、地上局から見て幾何的には成立するが実用上あり得ない長距離・低空の「かすめる」GSL リンクが最短経路に選ばれてしまう不具合が確認された。これを避けるため、GSL にも ISL と共通の `maxRangeKm` による距離上限を適用するように変更した(`losMarginKm` は ISL 専用のまま)。

#### 1.2.2 ISL の存在条件

衛星 i, j の ECI 位置を r_i, r_j [km] とし、次の 3 条件の AND とする。

**(a) 地球遮蔽なし (Line of Sight)**

線分 r_i–r_j が「地球 + 大気マージン」球に交差しないこと。線分と地球中心 O(ECI 原点)の最短距離 d_min で判定する。

```
d      = r_j - r_i
t*     = clamp( dot(-r_i, d) / dot(d, d), 0, 1 )
p_near = r_i + t* · d
d_min  = |p_near|

LoS 成立 ⟺ d_min > R_e + h_margin
```

- R_e = 6378.137 km(赤道半径。安全側の評価になる)
- h_margin: 大気減衰・屈折を避けるためのグレージング高度マージン。既定 80 km、ユーザー設定可。
- t* のクランプが重要: クランプなしの「直線と球」の判定では、地球の反対側に伸ばした直線が球と交差するだけで偽陰性になる。線分判定にすることで、近接した 2 衛星や GEO–GEO のような長距離リンクも正しく扱える。

**(b) 最大リンク距離**

```
|r_j - r_i| <= d_max
```

d_max は通信端末の能力を表すパラメータ。既定 5,000 km(LEO 光 ISL の典型値のオーダー)、ユーザー設定可。LEO–GEO のような異種軌道間リンクでは距離スケールが桁で違うため、シェルペアごとの上書きを許す(§2.4)。

**(c) パターン制約(任意)**

実運用のコンステレーションでは、ISL 相手は自由選択ではなく端末配置で決まる(例: Starlink の +Grid)。ユーザーがシェルごとにリンク方式を選ぶ:

- `dynamic`: (a)(b) を満たす全ペアが候補。自由トポロジ。
- `gridPattern`: 同一面内の前後 2 機(平均近点角順)+ 隣接面の同スロット 2 機、の最大 4 リンクに限定。その上で (a)(b) も適用する。

`gridPattern` は物理的に現実的なだけでなく、候補生成が O(N) になるため大規模時の高速化手段でもある(§1.7.3)。

**指向制約(スルーレート、視野角、太陽方向回避など)は初期スコープ外**とし、将来 (c) の拡張として追加できる構造にしておく。

### 1.3 時変グラフの扱い — スナップショット近似

#### 1.3.1 スナップショットで十分な理由

信号の伝播遅延は LEO 多段経由でも数十 ms のオーダー。一方、トポロジ(エッジ集合)が変化するタイムスケールは数秒〜数分。つまり

```
伝播時間 (~10^-2 s) << トポロジ変化時間 (~10^1–10^2 s)
```

であり、パケットが経路を通過する間にグラフは実質不変。よって **各時刻 t で静的グラフ G(t) を作り最短経路を解く「スナップショットモデル」** が第一近似として正当化される。store-and-forward(衛星でデータを保持して可視待ちする運用)を扱わない限り、時間展開は不要。

#### 1.3.2 将来拡張: 接触プランと時間拡張グラフ

蓄積転送や「時間窓をまたぐ配送」を扱いたくなった場合は、各エッジの可視時間窓リスト(contact plan)を作り、Contact Graph Routing (CGR) や時間拡張グラフ(time-expanded graph)に移行する。本設計では §1.5.2 の「残存可視時間の予測」が contact plan 計算の部分集合になっており、自然に拡張できる。初期実装のスコープには含めない。

### 1.4 エッジコストと multi-objective

#### 1.4.1 設計方針: 「等価遅延 [ms]」への統一

多目的の重み付き和は、各目的の単位・スケールが揃っていないと重みの意味がユーザーに伝わらない。そこで **全コスト成分を「等価遅延 ms」に換算して合算する**。ユーザー設定値も物理的に解釈可能な量になる。

```
c(e) = ( c_prop(e) + c_hop(e) + c_kind(e) + c_stab(e) ) × H(e)   [ms]

H(e) = 1 - β   (e が前回採用経路に含まれる場合。ヒステリシス、§1.5.1)
     = 1       (それ以外)
```

#### 1.4.2 コスト成分の定義

| 成分 | 種類 | 定義 | ユーザー設定 | 既定値 |
|---|---|---|---|---|
| 伝播遅延 c_prop | 加算 | distance_km / 299792.458 × 1000 | なし(物理量) | — |
| ホップペナルティ c_hop | 加算 | 一定値/エッジ(中継処理・キューイング相当) | hopPenaltyMs | 2 ms |
| リンク種別ペナルティ c_kind | 加算 | エッジ種別(GSL / ISL、シェル別)ごとの加算値 | kindPenaltyMs | 0 ms |
| 安定性ペナルティ c_stab | 加算 | 残存可視時間ベース(§1.5.2、Phase 4) | stabilityWeight ほか | 0(P4 まで無効) |
| ヒステリシス H(e) | 乗算 | 前回経路エッジへの割引(§1.5.1、Phase 2) | switchDiscount β | 0.2 |

- c_hop はエッジごとに課金する。どの A–B 経路もエッジ数 = 経由衛星数 + 1 なので、「経由衛星ごとに課金」とは定数差しかなく最適経路は変わらない。表示上のホップ数は経由衛星数と定義する(§5)。
- ホップペナルティを大きくすれば「ホップ数最小」寄り、0 にすれば「純遅延最小」寄りになり、スライダ 1 本で hop / latency のトレードオフを表現できる。
- c_kind により「GEO 経由は避けたい」「特定シェルを優先したい」等のポリシーを表現する(例: GEO 絡みのエッジに +50 ms)。

#### 1.4.3 multi-objective の扱い

- **初期実装: 重み付き和のスカラー化**。全成分非負なので Dijkstra がそのまま使える。ユーザーは §2.5 の UI で hopPenaltyMs / kindPenaltyMs / switchDiscount を変更し、経路が変わる様子をインタラクティブに観察できる。
- **厳密なパレート最適化(多目的ラベリング法、ε 制約法、k-shortest paths + 事後評価)は将来拡張**。パレートフロントの列挙は最悪指数個の解を持ち計算も UI も重くなるため、まず重み付き和で運用し、需要が確認できたら「遅延 vs ホップ数のパレート図」を解析パネル(§2.5.4)に追加する形とする。

### 1.5 経路安定性(頻繁な切り替えの抑制)

「その瞬間の最適」だけを毎回選ぶと、コストが拮抗した経路間でフラッピング(高頻度な張り替え)が起きる。2 つの手法を段階導入する。

#### 1.5.1 ヒステリシス(Phase 2)

直前の採用経路 P_prev に含まれるエッジのコストを割引く。

```
c'(e) = c(e) × (1 - β)   if e ∈ P_prev
      = c(e)             otherwise
β = switchDiscount ∈ [0, 0.5]、既定 0.2
```

- 新経路が「β 割引を覆すほど」良い場合のみ切り替わる。β が実質的な切替閾値になる。
- 割引後もコストは非負なので Dijkstra の前提を壊さない。
- 実装が軽く(前経路のエッジ集合を Set で持つだけ)、状態も 1 世代分で済む。
- 注意: これは切替回数の厳密な最小化ではなく貪欲な抑制である。厳密化(時間区間全体での切替回数最小化)はオフライン問題になり、初期スコープ外とする(§1.3.2 の contact plan 導入後に検討可能)。

#### 1.5.2 残存可視時間ペナルティ(Phase 4、軌道予測の活用)

軌道要素は既知なので、各エッジ e について「今後も存在条件を満たし続ける残り時間 τ_e」を予測できる。

```
τ_e = min{ Δt > 0 : 時刻 t + Δt で条件 (a) or (b) が破れる }
```

計算法: t から前方ホライズン T_h(既定 300 s)を粗い刻み(既定 10 s)でサンプリングし、最初に条件が破れた区間を二分法で精密化する。破れなければ τ_e = T_h(打ち切り)。

ペナルティは「もうすぐ切れるリンクを避ける」形の単調減少関数で与える:

```
c_stab(e) = w_τ × max(0, 1 - τ_e / τ_min)   [ms]
τ_min: 安定とみなす残存時間の閾値(既定 60 s)
w_τ  : ペナルティ上限(既定 20 ms)
```

ヒステリシス(受動的な切替抑制)と残存時間(能動的な予防)は独立に効くため併用できる。コスト計算が全エッジ × 前方サンプリングになる点だけ重いので、Phase 4 で Worker 前提とする(§2.7)。

### 1.6 探索アルゴリズム

#### 1.6.1 基本: 二分ヒープ Dijkstra

- 全コスト成分が非負なので Dijkstra が適用可能。計算量 O((|E| + |V|) log |V|)。
- 規模感: N = 2,000 機、平均次数 k = 10 なら |E| ≈ 2×10^4。1 回の探索は 1 ms 未満〜数 ms であり、**探索自体は支配項にならない**(支配項は候補リンク生成。§1.7)。
- 始点 A・終点 B の単一ペア探索なので、B に到達した時点で打ち切れる。

#### 1.6.2 A* による枝刈り(任意最適化)

ヒューリスティックとして「ノード v から地点 B までの直線距離を光速で割った値」を使う:

```
h(v) = |r_v - r_B| / c   [ms]
```

実経路長は直線距離以上、かつ他のコスト成分は全て非負なので h は admissible(過小評価)であり、最適性を保ったまま探索ノード数を減らせる。実装は Dijkstra の優先度キーを g+h に変えるだけ。

注意: ヒステリシス(§1.5.1)併用時は割引後コストが d/c を下回り得るため、そのままの h は admissible でなくなる。併用する場合は h(v) に (1 − β) を乗じて過小評価性を回復する。Phase 1 では Dijkstra で開始し、プロファイリングで探索時間が効いてきたら導入する(規模見込みからは不要の公算が大きい)。

#### 1.6.3 再計算周期

- 毎フレーム再計算は不要。トポロジ変化のタイムスケール(秒〜分)に合わせ、**シミュレーション時間で recomputeIntervalSimS(既定 10 s)ごと**に再計算する。
- 倍速再生(`SpeedControl` の最大 600×)ではシミュレーション 10 s = 実時間 約 17 ms になるため、**実時間の下限インターバル(既定 200 ms)** を併設して二重にスロットルする。高倍速時は実時間側が支配する。
- 一時停止中はシミュレーション時刻が進まないため定期再計算は止まる。ただし**設定変更(地点・参加衛星・コスト)は一時停止中でも即時に 1 回再計算**する。
- 再計算の谷間のフレームでは、経路の**ノード列は固定のまま、線分端点の座標だけ**を毎フレーム更新する(衛星は動き続けるため)。これは既存の linkLines と同じ更新パターン(§2.3)。
- 再計算時に経路の存在条件が既に破れていることは起こり得る(見た目上、線が地球をかすめる等)。recomputeIntervalSimS を小さくすれば軽減され、Phase 4 の残存時間ペナルティが根本対策になる。

### 1.7 候補リンク生成の高速化

元要求で明示されている重点項目。ナイーブな全ペア判定は O(N^2) で、N = 1,000 なら約 5×10^5 ペア(1 ペアあたり十数 flop なので数 ms、実用範囲)、N = 10,000 なら 5×10^7 ペアで JS では 100 ms を大きく超え、破綻する。段階的に 3 つの手法を使う。

#### 1.7.1 ナイーブ全ペア(Phase 1)

N ≤ 2,000 の想定でそのまま実装する。**このコードは以後も「正解生成器」としてテストで使い続ける**(§3.1)。早い段階の最適化で正しさの基準を失わないため、必ず最初に作る。

判定順序による定数倍削減: 距離二乗判定(sqrt 不要)→ LoS 判定、の順で早期棄却する。

```
d2 = |r_j - r_i|^2
if d2 > d_max^2: 棄却            # 乗算3回+比較のみ
else: LoS 判定 (§1.2.2 (a))
```

#### 1.7.2 一様グリッド(uniform grid)による空間分割(Phase 3)

- ECI 空間をセル一辺 L = d_max のボクセルに切り、各衛星をセルにハッシュ登録(O(N))。
- 各衛星は自セル + 隣接 26 セルの衛星とだけペア判定する。|r_j - r_i| ≤ d_max のペアは必ず隣接セル内にあるため、**取りこぼしなし**(正しさはナイーブ実装との一致テストで担保する。§3.1)。
- 計算量は O(N + Σ 近傍ペア数)。衛星は薄い球殻に分布するので、セルあたりの占有数は N に対して緩やかにしか増えない。
- k-d tree / octree でも良いが、毎スナップショットで全点が動く用途では再構築 O(N) の一様グリッドが最も単純で速い。木構造の逐次更新は複雑さに見合わない。
- グリッドはシェルごとの d_max の最大値で切る(異種軌道間対応)。

#### 1.7.3 パターン制約による構造的削減(Phase 3)

`gridPattern` シェル(§1.2.2 (c))は、候補が「面内前後 2 + 隣接面 2」と構造で決まるため、候補生成が **探索なしの O(N)** になる。生成時にシェル定義(`ConstellationShell` の planes / count / phasing)から各衛星の (面番号, スロット番号) を割り当てておけば、隣接関係は添字計算だけで求まる。大規模 Walker コンステレーションではこれが最速かつ最も現実に近い。

#### 1.7.4 時間コヒーレンス(Phase 3 の任意最適化)

エッジ集合は連続的にしか変化しないため、毎回ゼロから作らず「前回の候補集合 + グリッド近傍の差分」だけ再チェックする手がある。ただし一様グリッド + 型付き配列の実装が十分速ければ不要。**実測してから導入判断**とし、投機的には実装しない。

#### 1.7.5 データレイアウト

位置は `Float64Array`(x0, y0, z0, x1, ...)のフラット配列で持ち、オブジェクト生成を避ける。これは Worker への転送(transferable / 構造化クローン)とも相性が良い(§2.7)。

### 1.8 座標系・時刻・数値精度

- **計算は ECI [km] で統一する。** satellite.js の `propagate` 出力をそのまま使い、変換を最小化する。
- 地上地点は geodetic → `geodeticToEcf` → `ecfToEci(ecf, gmst)` で ECI 化する(gmst = `satellite.gstime(simDate)`、既存パターン)。
- GSL の仰角判定のみ ECF 系の既存関数(`ecfToLookAngles`)を使う。同一 simDate から得た gmst を共有すれば整合する。
- 描画時のみ既存のシーン座標変換を適用する。軸の入替(X_scene = X_eci, Y_scene = Z_eci, Z_scene = −Y_eci)に加え、**正規化が非等方**である点に注意(X, Z は赤道半径、Y は極半径で除算。`src/lib/visualization.ts` の衛星点更新と同一)。経路頂点にも必ず同じ変換を使わないと、衛星点と線の端点がずれる。**グラフ計算モジュールにシーン座標を持ち込まない。**
- 1 スナップショットの全ノード位置は**同一の simDate で評価**する(フレームをまたいだ位置の混在はエッジ判定を不整合にする)。

### 2.4 データモデル(型案)

```ts
// src/lib/isl/types.ts(案)
export interface IslEndpoint {
  kind: "station" | "adhoc";
  name: string;                 // 表示名
  latitudeDeg: number;
  longitudeDeg: number;
  heightKm: number;
  minElevationDeg: number;      // 既定 10
}

export interface IslLinkModel {
  mode: "dynamic" | "gridPattern";
  maxRangeKm: number;           // 既定 5000
  losMarginKm: number;          // 既定 80
}

export interface IslSettings {
  enabled: boolean;
  endpointA: IslEndpoint | null;
  endpointB: IslEndpoint | null;
  // 参加衛星: シェル単位 + 個別衛星(satellites.toml 由来)の選択
  participantShellKeys: string[];   // 安定キー(下記注意参照)
  participantSatnums: number[];     // toSatrec() 後の satrec.satnum を識別子に使う
  linkModel: IslLinkModel;                       // 全体の既定
  shellLinkModels?: Record<string, Partial<IslLinkModel>>; // シェル別上書き(P3)
  cost: {
    hopPenaltyMs: number;       // 既定 2
    switchDiscount: number;     // β、既定 0.2 (P2)
    kindPenaltyMs?: Record<string, number>;      // シェル/GSL 別加算 (P2)
  };
  recomputeIntervalSimS: number; // 既定 10
}

// グラフ内ノード id: 0..N-1 = 衛星 index、N = 地点 A、N+1 = 地点 B(実装時に定数化)
export interface IslPathEdge {
  fromNodeId: number;
  toNodeId: number;
  kind: "gsl" | "isl";
  distanceKm: number;
  delayMs: number;
}

export interface IslPathResult {
  reachable: boolean;
  computedAtSimMs: number;
  nodeSatIndices: number[];     // 経由衛星の index 列(A, B は暗黙の端点)
  edges: IslPathEdge[];
  totalDelayMs: number;
  totalDistanceKm: number;
  hopCount: number;             // 経由衛星数
  switchedFromPrevious: boolean;
  candidateEdgeCount: number;   // 診断用: そのスナップショットのエッジ総数
  computeTimeMs: number;        // 診断用
}
```

- 異種軌道混在(LEO/MEO/GEO)は `shellLinkModels` で d_max 等をシェル別に上書きして表現する。シェルペアごとの完全なマトリクス設定は複雑すぎるので、**両シェルの maxRangeKm の大きい方**を採用する簡易則で開始する。
- `gridPattern` はシェル内リンクにのみ適用され、シェルをまたぐリンクは常に `dynamic` 判定とする(面/スロット構造がシェル間では定義できないため)。
- **シェルの安定キーについて(重要)**: 現状の `ConstellationShell.id` はパース/生成のたびに `crypto.randomUUID()` で再発行されるため、localStorage への永続参照には使えない。設定の保存には**シェルの配列 index(+ name があれば併記)を安定キー**として使い、復元時に解決できなければ既定(全シェル参加)へフォールバックする。id を TOML に永続化する案はスキーマ変更(シリアライザ・`scripts/generate-satellites.ts` への波及)を伴うため、必要になった時点で別途判断する。
- **個別衛星の識別子**: `SatelliteSpec` の `"tle"` 型は satnum フィールドを持たないため、`toSatrec()` 後の `satrec.satnum`(TLE / elements のどちらでも得られる)を識別子とする。satnum 重複時は警告のうえ両方を参加させる。
- `minElevationDeg` の既定 10° は臨時地点用(通信リンクの典型値)。既存局を選んだ場合はその局の `minElevationDeg` をそのまま使う(既存の `normalizeVisibilityCriteria` の既定 0° とは用途が異なる意図的な差)。

**設計変更(Phase 5, isl-routing-review.md H-1/H-2/H-4/H-5/S-1)**: 上記 `participantShellKeys`/`participantSatnums` は実装せず、代わりに以下へ差し替えた。

```ts
export interface IslSettings {
  // ...
  excludedShellKeys: string[];      // 除外するシェルの安定キー(IslShellRange.key)
  includeBaseSatellites: boolean;   // satellites.toml 由来の個別衛星を含めるか
  // participantShellKeys / participantSatnums は削除
}
```

- `participantSatnums`(satnum への事前解決スナップショット)は、TOML 再パースのたびに satnum が 1 から振り直される(`tomlParsers.ts`)ことと、UI コンポーネントのマウント状態に依存して更新タイミングがずれることの二重の理由で陳腐化しやすく、実際に「新しい衛星配列に古いスナップショットを適用してしまう」バグ(H-4)と「全解除が全参加に反転する」バグ(H-2、空配列の意味が「フィルタなし」と衝突)の根本原因になっていた。
- 解決策は元々の設計意図(本節末尾の「シェルの安定キーについて」の注記)に忠実に戻すことで、除外シェルキー + 個別衛星フラグという**小さく安定した状態**だけを保存し、実際の衛星 index への解決は compute 直前(Worker/graph 層、`isl/participants.ts` の `resolveIslParticipantIndices`)に**毎回**行う。解決は satnum ではなく **shellRanges の index range** に対して行うため、satnum の重複や Alpha-5 形式(L-2)の影響も受けない。
- `shellRanges`(`IslShellRange[]`)自体も `IslSettings` から外し、localStorage には一切永続化しない。`satellites.length`/`shellRanges` を生成する唯一の場所(`SatelliteEditor.handleUpdate`、内部で `tomlParsers.ts` の `generateShellRanges` を呼ぶ)で衛星配列と同時に導出し、App state として一体で保持することで、「衛星配列と shellRanges が別々のタイミングで更新されてずれる」余地を構造的に排除した。
- `tomlParsers.ts` の `generateFromShells` 自体にも既存バグがあった(H-1): シェルごとの内側ループが**累積**の `sats.length < count` で打ち切っていたため、2 番目以降のシェルが切り詰められていた(ISL 機能に限らず、多シェル constellation.toml では表示衛星数自体が仕様より少なかった)。シェルごとの生成数を個別に数える形へ修正済み。

### 2.5 UI/UX 設計

#### 2.5.1 設定の置き場所(決定: 新規「ISL」タブ)

設定 UI は、左パネルのタブ列(編集 / 解析 / 設定)に**新規「ISL」タブを並列追加**する(**決定済み**)。

- 根拠: この機能は「常時表示のシーン装飾」(設定タブ的)でも「オンデマンド解析」(解析タブ的)でもなく、入力 → 常駐計算 → シーン表示 + 数値表示という独立したワークフローを持つ。専用タブなら設定(地点・対象・コスト)と結果(メトリクス)を 1 箇所に集約でき、既存タブの肥大化も防げる。
- 例外 1: Phase 4 の時間軸解析(時間窓スイープによる切替統計)は性質がオンデマンド解析なので、AnalysisTab に置く(§2.5.4)。
- 例外 2: 経路線の色設定は、他の色設定と同じく OptionTab(設定)に置く(§2.5.3)。

実装メモ: タブは `src/components/ui/SatelliteEditor.tsx` 内(Radix 風の `tabs.tsx`)で実装されており、現状は 編集 / 解析 / 設定 の 3 タブ。`TabsList` の grid-cols-3 固定と、タブ value の union 型 `"editor" | "analysis" | "option"` の拡張(grid-cols-4 化 + `"isl"` 追加)が必要になる(小変更)。Phase 1 の UI 作業はこのタブ追加から始める。

**設計変更(Phase 10, UI/UX 再設計)**: 実装・運用後の UI レビューで「ISL というタブ名だけ抽象度が違い初見で中身が想像できない」「機能が ISL/設定/解析の 3 タブに分散している」という課題が確認されたため、以下のとおり変更した。

- タブ名を **シナリオ / 通信 / 解析 / 表示** に再編(旧: 編集 / 解析 / ISL / 設定)。ISL 経路探索は「通信」タブに置き、通信系の表示設定(経路色、地上局の通信範囲コーン)も同タブへ集約した。内部のタブ value(`"editor" | "analysis" | "isl" | "option"`)は互換のため変更していない。
- 通信タブ内部をタスク指向の 5 セクション(経路探索 / 結果 / 経路の重み付け / 詳細設定 / 診断)に再構成。無効時は経路探索(地点選択 + トグル)と通信範囲コーンのみを表示し、結果セクションを設定より上に置いた。地点未設定で有効化した場合はガイドを表示する。
- **結果 HUD の追加**(`src/components/ui/IslHud.tsx`): 有効時はシーン右下(時刻表示の上)に地点名・総遅延・ホップ数・切替回数の小カードを常駐表示する。パネルを閉じていても経路メトリクスが見え、クリックで通信タブが開く。
- 例外 2(色設定は OptionTab)は**撤回**し、経路色は通信タブの詳細設定内へ移設。結果カードから解析タブの「ISL経路タイムライン解析」を直接開く導線も追加した。

#### 2.5.2 ISL タブの構成(上から順)

1. **有効化トグル** — OFF 時は計算も描画も完全停止(ゼロコスト)。
2. **地点 A / 地点 B** — それぞれ「既存地上局から選択(ドロップダウン)」または「臨時地点(緯度・経度・高度・最低仰角を直接入力)」。臨時地点フォームは `GroundStationForm` の入力部品を再利用。A/B の入替ボタン(経路は無向なので結果は同じだが、表示ラベルの利便のため)。
3. **参加衛星** — シェル一覧のチェックボックス(既定: 全シェル ON)+ 個別衛星(satellites.toml 由来)の含否。シェルごとの詳細(リンク方式 dynamic/gridPattern、maxRangeKm、losMarginKm 上書き)は行の展開で表示(P3)。
4. **コスト設定(P2)** — hopPenaltyMs スライダ(0–20 ms)、switchDiscount スライダ(0–50%)、リンク種別ペナルティ。変更は即時再計算に反映し、経路の変化をその場で見せる。
5. **結果カード** — 到達可否 / 総遅延 ms / ホップ数 / 総距離 km / 直近の切替からの経過(sim 時間)/ 累積切替回数。経路の衛星名リスト(クリックで該当衛星を選択 = 既存の選択機構と連動)。
6. **診断(折りたたみ)** — 候補エッジ数、計算時間 ms、再計算間隔設定。

到達不能時は結果カードに「経路なし」を明示し、シーン上の経路線を消す(古い経路を残さない)。

#### 2.5.3 3D シーン表示

- **経路線**: GSL 区間と ISL 区間を色分け(既定: GSL = マゼンタ系、ISL = シアン系。OptionTab の色設定に項目追加)。既存 linkLines より太く/明るくして「その他の可視リンク」と区別する。
- **経由衛星のハイライト**: 経路上の衛星を強調(既存の選択ハイライトと同系の手法)。
- **地点 A/B マーカー**: 既存の地上局マーカー描画を再利用。臨時地点も同じ見た目で表示。
- **切替の視覚化(P2)**: 経路張り替えの瞬間に旧経路を短時間フェードアウトさせる等の演出は任意。まずは切替回数カウンタで足りる。

#### 2.5.4 解析パネル(P4)

`IslRoutingAnalysis.tsx`: 時間窓(開始時刻・時間・刻み)を指定して Worker でスイープし、
- 総遅延・ホップ数の時系列チャート(ECharts)
- 切替イベントのタイムライン
- 到達可能率(時間比)
を表示。CSV/PNG ダウンロードは既存 `analysis/utils` を再利用。

#### 2.5.5 設定の永続化

- IslSettings は `viewState.ts` の枠組みで localStorage に保存(カメラ・表示設定と同格)。
- TOML バンドル(`config.ts`)への含有は、設定ファイル共有の需要が出た時点で対応(P3 以降の判断)。**satellites.toml / constellation.toml のスキーマは変更しない**ため、`scripts/generate-satellites.ts` への影響はない。

### 2.6 描画設計

- 経路は最大ホップ数を仮定できないため、**単一の `THREE.LineSegments` + 十分な容量の BufferAttribute を事前確保**し、`setDrawRange` で使用区間を制御する(既定容量 64 区間。超過時のみ再確保)。頂点を区間ごとに複製する(2 頂点/区間)ことで、GSL/ISL の色分けを頂点カラーで濁りなく行える(LineStrip だと区間境界の頂点で色が線形補間されてしまう)。1 本のジオメトリで済む点は同じ。
- 毎フレーム: ノード列(再計算間隔で固定)に対応する衛星のシーン座標を satPosAttr から読んで頂点を更新。地上端点は地球の自転に追従(既存の地上局マーカーと同じ扱い)。
- リソースは `SatelliteScene.dispose()` の disposeFns 配列に登録し、GPU リークを防ぐ(CLAUDE.md の注意事項)。
- 経路計算モジュールとの結線: `SatelliteScene.updateParams()` の「非構造パラメータの live 更新」経路に IslSettings を載せ、シーン再構築を発生させない(直近コミット「Apply non-structural scene params without rebuild」の方針に合わせる)。

### 2.7 パフォーマンス設計と目標値

| 項目 | Phase 1(メインスレッド、naive) | Phase 3(Worker、grid/pattern) |
|---|---|---|
| 想定規模 N | ≤ 2,000 | ≤ 10,000 |
| 候補生成 + 探索 | < 30 ms / 再計算 | < 100 ms / 再計算(Worker 内) |
| フレームレート | 60 fps 維持(再計算はフレームをまたいでも良い) | 60 fps 維持 |
| 再計算頻度 | sim 10 s ごと & 実時間 ≥ 200 ms | 同左 |

- Phase 1 で 30 ms かかっても、再計算は 200 ms に 1 回以下なので体感上のカクつきは限定的。それでも許容できない場合は Phase 3 の Worker 化を前倒す。
- Worker への入力は「衛星 spec(初回のみ)+ simDate + 設定」とし、Worker 側で伝播する。位置配列を毎回転送するより転送量が小さく、Phase 4 の時間スイープも同じ Worker で実行できる。
- メモリ: 位置・隣接リストは型付き配列(Float64Array / Int32Array)でフラットに持ち、再計算ごとの GC 圧を抑える。

## 3. 検証計画

### 3.1 ユニットテスト(bun:test、`tests/` に追加)

CLAUDE.md の規約どおり `bun:test` を使用し、決定論的フィクスチャで書く(`orbitalCoordinates.test.ts` の様式)。

**isl-geometry.test.ts**
- 同一軌道面上の近接 2 衛星(LEO 550 km、離角 10°)→ LoS 成立。
- 対蹠位置の 2 衛星(LEO)→ 地球遮蔽で LoS 不成立。
- 接線ぎりぎりのケース: d_min = R_e + h_margin ± ε(手計算で配置を構成)→ 境界の両側で判定が反転。
- 線分クランプの検証: 非常に近い 2 衛星(直線延長は地球と交差するが線分は交差しない配置)→ LoS 成立。クランプを外すと偽になる配置を明示的に置く。
- GEO–GEO 離角 90° → LoS 成立、離角 165°(幾何限界超)→ 不成立。※GEO の遮蔽限界は中心角 2×acos(R_e/r_geo) ≈ 162.6°(h_margin = 0 のとき。h_margin = 80 km 込みでは 2×acos((R_e+80)/r_geo) ≈ 162.4°)。
- 距離条件: |r_j − r_i| が d_max ± ε の両側。

**isl-candidates.test.ts**
- naive と uniformGrid の**完全一致**(プロパティテスト的): 疑似乱数(シード固定)で球殻上に N = 300 点を配置 × 複数シード × 複数 d_max で、エッジ集合が一致すること。セル境界をまたぐペアの取りこぼし検出が主目的。
- gridPattern: Walker シェル(例 planes=6, count=66)で各衛星のリンク相手が「面内前後 2 + 隣接面同スロット 2」であること、面番号の巻き戻り(plane 5 ↔ plane 0)とスロットの巻き戻りが正しいこと。
- 参加選択: 除外したシェル/衛星がエッジに現れないこと。

**isl-shortestPath.test.ts**
- 手作りの小グラフ(5–10 ノード)で既知の最短経路・コストに一致。
- 非連結グラフ → reachable = false。
- A と B が同一衛星を介して直結するケース(ISL 0 ホップ、GSL 2 本)。
- ヒステリシス: 旧経路コスト 100、新経路コスト 85、β = 0.2 → 旧経路維持(100×0.8 = 80 < 85)。新経路コスト 75 → 切替。境界値 80 ちょうどの扱い(タイは旧経路維持と定義)も固定する。
- コスト成分: hopPenaltyMs を 0 → 大 に振ると「ホップ数は多いが距離の短い経路」から「ホップ数最小経路」へ切り替わる 2 経路グラフ。

**isl-graph.test.ts**
- 決定論的配置(円軌道の解析的な位置)から、GSL/ISL エッジ集合とコストが期待どおり構築されること。
- 地上端点の ECI 位置が gmst を介して正しいこと(赤道直下・経度 0° の地点を epoch 固定で手計算比較)。

### 3.2 数値検証シナリオ(結合テスト / スクリプト検証)

**シナリオ 1: GEO 2 機リレー(手計算との一致)**
- 配置: GEO 衛星を東経 0° と東経 90° に(elements 指定、e = 0)。地点 A = (0°N, 0°E)、地点 B = (0°N, 90°E)、いずれも直下点。
- 期待値(幾何のみの手計算):
  - GSL 各 35,786 km → 片道 119.4 ms
  - ISL 弦長 = 2 × 42,164 × sin(45°) ≈ 59,629 km → 198.9 ms
  - 合計 ≈ 437.6 ms + ホップペナルティ分(エッジ 3 本)
- 許容誤差: SGP4 の摂動と elements→TLE 変換誤差を考慮し、距離で ±0.5% 程度。epoch 直後の時刻で評価する。

**シナリオ 2: Iridium 風 Walker(オーダー確認)**
- 66 機(6 面 × 11 機)、高度 780 km、傾斜角 86.4°。地点 A = 東京、地点 B = ニューヨーク。
- 検算: 総遅延の下限は大圏距離 ≈ 10,850 km / c ≈ 36.2 ms。経路遅延がこの下限以上、かつ 2 倍(≈ 72 ms)以下に収まること、ホップ数が数ホップ〜十数ホップのオーダーであることを確認する(文献の Iridium/Starlink 系解析と整合するオーダー)。
- このシナリオは `scripts/` の検証スクリプト(例 `scripts/verify-isl-routing.ts`)として残し、回帰確認に使う。

**シナリオ 3: 到達不能**
- 参加衛星を極軌道 1 面だけに絞り、地点を可視圏外に置く → reachable = false が返り、UI が「経路なし」を表示。

**シナリオ 4: 切替抑制の時系列(P2)**
- Walker シェルで 10 分間を 10 s 刻みでスイープし、β = 0 と β = 0.2 の切替回数を比較。β = 0.2 で切替回数が有意に減り、総遅延の劣化が小さい(例: +5% 以内)ことを確認。閾値は最初の実測で較正する。

### 3.4 UI・表示の手動検証チェックリスト

- 経路線が地球を貫通して見えるフレームがない(再計算間隔内のドリフト許容量の目視確認)。
- 倍速 1× / 100× / 一時停止で経路と再計算が破綻しない(停止中は再計算も止まる)。

## 5. 用語

- **ISL**: Inter-Satellite Link。衛星間通信リンク。
- **GSL**: Ground-Satellite Link。地上局(地点)と衛星のリンク。
- **+Grid**: 面内前後 2 機 + 隣接面 2 機と結ぶ代表的な ISL トポロジ。
- **スナップショットモデル**: 時変グラフを各時刻の静的グラフの列として扱う近似。
- **Contact Graph Routing (CGR)**: 可視時間窓(contact plan)を前提とした DTN 系経路制御。本設計では将来拡張。
- **ヒステリシス**: 現状維持側に閾値を設けて頻繁な状態遷移を防ぐ機構。
